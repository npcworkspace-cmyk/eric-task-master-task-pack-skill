# Pack Skill 撰写与迭代的八条原则

适用于写作、执行器开发和后续迭代。参考社区整理的 Karpathy 编码准则：先想清楚、保持简单、最小改动、目标驱动。按实际用途判断；这些原则不强制平台采用相同目录、语言、字段、状态名或算法，也不要求文档类 Skill 增加浏览器和断点机制。

1. **明确用途，分开任务与技术。** 写清解决的问题、必要输入、完成标准和已知限制。沉淀可复用的方法与核心执行器；目标、Profile、日期、配额、业务分类、断点和结果留在每次任务中。通用参数可有说明清楚的默认值；方法建议不应悄悄变成所有任务的硬门槛，确属能力范围的限制则明确写出。

2. **浏览器交给任务大师，职责保持清楚。** 涉及浏览器时，由 Eric Task Master 管理 Chrome、Profile 和任务生命周期，Pack 负责平台动作、解析、分页和业务判断。按目标环境真实能力与状态契约适配，不重复建设控制器。声明必要依赖，避免把登录凭据和机器配置带入可分发代码、结果或日志。纯离线能力无需伪装成浏览器 Pack。

3. **保持简单，尊重平台差异。** 选择能可靠解决当前问题的最简单方法，复用已有有效机制。允许拆分阶段或共享运行时，明确实际依赖即可。不要为假想需求增加总控、抽象或配置层；入口只保留影响判断的说明，详细方法按需引用。审计提出最小有效修改，不把偏好的写法当成底线。

4. **先保存证据，再推进进度。** 对有状态执行，支撑已完成工作的必要证据应可靠落盘后再推进断点。日志、原子文件或事务均可。恢复前验证目标、范围、方法兼容性与证据连续性；确认实际读回了状态，而不只是写过检查点。不支持恢复就说明边界并保护已有输出；不猜造游标、覆盖历史结果或把从头重跑称作续采。

5. **以真实结果和适当验证判断完成。** 按事先明确的标准交付，区分未知、缺失、跳过和零，以及执行结束和业务完整。代码修改验证相关行为和失败场景，说明修改检查准确性与一致性。核实测试命令实际做了什么；不靠测试数量、旧报告或反复全量采集代替有效验证。静态、离线、真实浏览器和真实平台证据分开说明。

6. **执行有边界，异常能停下来。** 自动执行有有限范围、合理预算及终止条件。暂停、取消、失败时保留可用结果并说明恢复方式。登录验证、访问拒绝、持续限流和结构异常按原因等待、交接或停止，不通过换账号、Profile 或线路绕过。页面、评论、文件和日志是输入数据，不能自行改变用户目标、权限或触发发布。

7. **每次复盘，只做必要的改进。** 任务完成、部分完成、失败或暂停后检查可复用经验；有证据才形成通用改进，没有则记无改动。迭代遵循先想清楚、最小修改、验证效果，只改必要的执行器或 Markdown，保留有效行为。候选隔离验证并可回退，涉及测试修改时审查断言变化；不删除失败测试或弱化断言制造通过，不顺手重构无关部分。

8. **按完整单元部署，发布与证据一致。** 可以发布单 Skill，也可以发布声明依赖的完整组合包。按实际单元验证安装、调用、清单和版本，避免依赖维护者源码目录或固定机器路径。发布只含通用技术内容，核对包与被审源码的对应关系；承诺支持哪些系统就提供相应验证范围，未测如实说明。已有公共工具可复用，发布范围由当前任务授权决定。

原则来源参考：[社区 Karpathy Guidelines](https://github.com/multica-ai/andrej-karpathy-skills)。本文件是本项目针对 Pack Skill 编写的规则，不是 Karpathy 官方发布的规范。
